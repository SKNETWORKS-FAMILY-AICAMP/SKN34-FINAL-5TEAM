# 최종 프로젝트 가이드 적용 계획

- 기준일: 2026-10-16
- 기준 자료: 사용자가 제공한 [최종 프로젝트 가이드 원문](최종프로젝트_가이드_원문.md)
- 문서 성격: 가이드의 제출 기준과 우리 서비스 기획을 연결하는 작업 기준. 강사 승인서나 구현 완료 보고서가 아니다.
- 이 문서를 추가하는 작업에서는 서비스 코드, 데이터, Git 원격 및 배포 설정을 변경하지 않는다.

## 1. 앞으로의 작업 기준

1. 기획·기능·일정을 변경하기 전에 이 문서와 가이드 원문을 확인한다.
2. 가이드에 명시된 필수사항, 예시·조건부 항목, 우리 팀의 제안사항을 구분한다.
3. 새 기능은 사용자 문제, 입력·처리·출력, 필요한 데이터, 평가 방법, 담당자와 일정을 먼저 정한다.
4. 구현·로컬 검증·배포 검증·강사 승인 상태를 별도로 기록한다. 코드나 기존 보고서가 있다고 완료로 표시하지 않는다.
5. 팀원과 합의하지 않은 범위 확장, 과도한 에이전트·인프라 추가를 피한다.
6. 상세 회의·공부 기록·아이디어는 노션에 정리하고, 저장소 `docs`에는 핵심 개발·운영·제출 기준을 남긴다.

## 3. 우리 서비스 기획

### 3.1 한 줄 정의

> 내 집 마련을 준비하는 사람이 청약·대출·자금계획 정보를 이해하고 활용할 수 있도록, 정보 수집·정리·계산을 자동화하고 대화형 분석·금융 학습·준비 리포트를 제공하는 서비스.

서비스 메시지는 **“내 집 마련, 모르는 채 결정하지 않도록”**이다. 손실 방지나 청약 당첨·대출 승인을 보장한다는 뜻이 아니다.

### 3.2 해결하려는 문제와 타깃

- 정보가 공고 기관·금융회사·교육 자료에 흩어져 있어 수집과 비교가 번거롭다.
- 공고와 상품 정보를 읽더라도 금융용어·조건·납부 시점을 이해하기 어렵다.
- 자신의 현금, 필요한 자금, 확인해야 할 조건을 하나의 준비 계획으로 연결하기 어렵다.
- 초기 핵심 타깃은 청약으로 내 집 마련을 준비하며 주거·금융지식의 보완이 필요한 사람이다.
- 니즈와 사용 의향은 가설이다. 조사 없이 실제 수요나 절감 효과가 입증됐다고 쓰지 않는다.

### 3.3 핵심 사용자 흐름

**내 조건 진단 → 공고 탐색 → 자금계획 → 금융정보·필요한 학습 → 질문과 근거 확인 → 준비 리포트 확인·저장**

첫 화면의 진단과 결과 확인 흐름을 유지하고, 결과 저장·지속 관리를 로그인과 연결한다. 화면은 기존 직방·뱅크샐러드 참고 방향의 가독성과 편의성을 유지하며 초기에는 PC 웹에 집중한다.

### 3.4 학습 범위

| 영역 | 학습 예시 |
|---|---|
| 경제·금융 역사 | 화폐, 은행, 금융시장의 변화와 전시형 이야기 |
| 사회 변화와 금융 | 베이비붐 세대, 고령화, 은퇴·연금 |
| 은행상품 | 예금·적금·대출·금리·신용 |
| 보험과 실제 활용 | 보장 구조, 약관 읽기, 청구 과정, 사례별 확인사항 |
| 투자 기초 | 주식·채권·펀드·ETF의 구조와 위험 |
| 디지털 금융 | 암호화폐의 개념, 변동성·보관·사기 위험 |
| 집 준비 | 청약, 계약금·중도금·잔금, 대출·상환 방식, 자금계획 |

콘텐츠 형식은 설명 → 생활 사례 → 확인 퀴즈 → 해설 → 추가 질문으로 구성한다. 금융아카데미 수강 경험은 구성에 참고하되 강의자료를 그대로 전재하지 않고, 사용 가능한 공식 자료로 내용을 직접 작성·검증한다. 이 전체 범위를 공부한다는 것과 첫 버전에 모든 상품·기능을 구현한다는 것은 구분한다.

## 4. 지정 주제에 맞춘 핵심: 대화형 분석과 자동 리포트

다음은 **추가 구현·검증이 필요한 설계안**이다. 기존 리포트 화면이나 인쇄 버튼만으로 지정 주제를 충족했다고 판단하지 않는다.

### 4.1 입력·처리·출력

| 단계 | 내용 |
|---|---|
| 입력 | 사용자의 명시적 질문, 선택한 공고, 사용자가 확인한 현금·소득·기존 부채 등 필요한 최소 입력, 계산 가정 |
| 대화형 처리 | 예: “이 공고를 준비하려면 언제 얼마가 필요한가요?”를 분류하고, 부족한 입력을 확인한 뒤 허용된 조회·계산 도구를 실행한다. |
| 데이터 분석 | 공고의 납부 일정과 입력 현금을 대조하고, 출처가 있는 상품 조건과 확인사항을 정리한다. 금액 계산은 결정론적 코드가 담당한다. |
| 설명 | LLM은 검색한 근거와 도구의 계산 결과를 설명한다. 없는 수치·일정·자격을 생성하지 않는다. |
| 출력 | 조건 요약, 선택 공고, 비용·일정, 자금 부족분, 확인할 대출 조건, 학습 항목, 출처·기준일·미확인 사항을 담은 준비 리포트 |

### 4.2 리포트 최소 구성

- 사용자 입력과 계산 가정 요약: 제공하지 않은 정보는 ‘미입력’으로 표시한다.
- 선택 공고와 공식 원문·정보 기준일.
- 확인된 계약금·중도금·잔금과 납부 일정: 없는 값은 ‘확인 필요’로 표시한다.
- 입력에 근거한 자금 차액·월 상환액 등 계산 결과와 사용한 계산식·가정.
- 대출 상품의 확인할 조건: 최종 한도·승인 결과로 표현하지 않는다.
- 원문 근거와 AI 설명을 구분한 요약, 확인할 서류·다음 행동 체크리스트.
- 모르는 개념에 연결된 학습 콘텐츠.
- 생성 시점·사용 데이터 버전·불확실성·최종 확인처.

저장·출력 형식과 갱신 방식은 팀 합의 후 정한다. 화면 자동 생성과 실제 파일 내보내기를 구분해 테스트한다. 시장 전망, 투자 수익, 당첨 확률을 보장하는 보고서는 만들지 않는다.

## 5. 필수 요소와 기술 역할

| 구분 | 가이드 기준 | 우리 적용안 | 확인·평가 |
|---|---|---|---|
| 필수 | 질문 입력·결과 출력 | 공고·금융정보에 대한 질문과 답변·근거·분석 결과·리포트 표시 | 입력 → 처리 → 출력 E2E 테스트 |
| 필수 | ML/DL 활용 기능과 학습·사용 결과물 | 기존 질문 분류 모델 및 청약 커트라인 회귀 모델의 재사용을 우선 검토 | 학습/평가 데이터 분리, 후보·베이스라인 비교, 서비스 사용 증거 |
| 필수 | 문서 검색(RAG) | 승인된 공고문·금융교육 자료의 검색과 출처 연결 | 검색 평가 세트, 근거 없는 질문, 문서 간 오염 테스트 |
| 필수 | LLM 답변 생성과 사용 이유 | 검색 근거·계산 결과를 쉬운 문장으로 설명하고 학습 질문에 응답 | 근거 일치·거절·숫자 보존·응답 시간·비용 평가 |
| 지정 주제 반영 | 대화형 데이터 분석·자동 리포팅 | 질문 → 데이터 조회·규칙 계산 → 근거 설명 → 준비 리포트 | 강사 적합성 확인과 실제 데이터 기반 시연 |
| 제출 항목 | 멀티 에이전트 아키텍처·테스트 | 역할별 라우팅·조회/계산 도구·검색/설명·리포트 구성의 최소 흐름을 설계 | 워크플로와 자율 에이전트를 구분해 설명하고, 인정 범위는 강사 확인 |
| 조건부/해석 확인 | 5주차 ‘(필요시) 자체 sLLM’, 본문 ‘3, 4번 주제 팀’ | 5팀 주제가 3번 주제 계열이므로 적용 여부와 대체 인정 여부를 강사에게 확인 | 필요할 경우 별도 데이터·학습·평가·자원 계획 수립. 자동으로 생략하거나 착수하지 않는다. |
| 공통 | 데이터 출처·품질·재현성·안정적인 웹 시연 | 수집 로그·스키마·버전·실행 안내·실패 처리·시연 영상 | 제출 파일 형식과 실제 실행 확인 |

주의사항:

- 사용자 청약가점은 규칙 계산이고, ML이 예측하는 것은 제한된 범위의 공고 커트라인이다. 둘을 ‘AI가 계산한 가점’으로 섞지 않는다.
- 기존 커트라인 모델의 학습 범위는 청약홈 APT 가점 결과다. 임대·보험·투자 판단으로 일반화하지 않는다.
- 모델을 Ollama로 다운로드·실행한 것은 자체 LLM 학습이나 파인튜닝 실적이 아니다.
- 단순 계산·필터·수집에 LLM을 강제로 쓰지 않는다. 담당 역할의 수가 늘어난다고 실행이 빨라지는 것도 아니다.
- 기술 스택 표의 여러 후보를 전부 도입하지 않는다. 기존 React·FastAPI·PostgreSQL·Chroma·LangGraph·Docker 구성을 우선 활용한다.
- GraphDB·Ontology·LoRA/Adapter 등은 가이드 예시·조건부 서술과 팀 주제 적용 여부를 확인한다. 필요한 산출물을 임의 면제하지도, 모든 예시 기술을 필수로 추가하지도 않는다.

## 9. WBS·역할·확인 양식 운영

### 9.1 작업과 역할

|---|---|---|---|

실제 WBS에는 담당자, 시작일, 종료일, 진행률을 반드시 채운다. 위 표는 계획 예시이며 실제 일정 배정이나 진행률을 뜻하지 않는다. 기획·금융자료 검증·개발·테스트·발표·통합 책임을 명확히 나누고 한 사람이 암묵적으로 모두 맡지 않는다.

### 9.2 강사 Confirm 전 보완

- 세부 주제·문제/기존 방식/불편·타깃: 이 문서 3~4절을 바탕으로 정리한다.
- 시장 규모·향후 규모: 미조사. 단위·연도·출처를 확인하기 전 수치를 만들지 않는다. 가이드에 따라 조사 제한 사항은 공란으로 둘 수 있다.
- 경쟁 서비스 3개·기능·BM·강점·한계: 조사 전. 청약홈·주거 플랫폼·금융정보/교육 서비스를 비교 후보로 검토한다. 직방·뱅크샐러드를 디자인 참고했다는 사실은 경쟁 분석 완료를 의미하지 않는다.
- 우리 핵심 기능·차별화: 집 준비 과정에 필요한 정보·계산·학습·근거·리포트를 연결한다는 가설이며 사용자 검증이 필요하다.
- BM·예상 한계: 미확정. 교육/정보 제공과 금융상품 광고·권유·중개를 혼동하지 않고 검토 후 제안한다.
- 기술 역할·데이터 소스: 5·7절을 기반으로 실제 확보 가능성을 증명한다.
- 팀원별 사용 의향(%)과 원하는 추가 기능: 각자가 답한다. 수치를 대신 작성하지 않는다.

## 10. 평가·시연 완료 기준

| 대상 | 평가 항목 | 기록 기준 |
|---|---|---|

| LLM | 근거 일치·숫자/단위 보존·근거 없는 질문 거절·안전성 | 생성 답변과 원문을 대조하고, 원문 대체 응답을 LLM 성공으로 세지 않음 |

| 성능·운영 | 지연·시간 초과·실패율·자원·비용 | 테스트 환경, cold/warm, 표본 수·측정 구간, 목표 대비 실제 |

지표 목표값은 측정 환경과 초기 결과를 보고 합의한다. 가이드의 ‘정확도 91%’, ‘응답 속도 20초’ 같은 예시를 우리 성과나 일괄 합격선으로 복사하지 않는다. 발표는 핵심 기능 2~3개에 집중하고, 비교·실패·한계·개선 계획과 실제 시연/대체 영상을 함께 준비한다.

- 관련 스크립트: [커트라인 학습](../backend/scripts/train_cutoff_model.py), [질문 분류 학습](../backend/scripts/train_intent.py), [분류 평가](../backend/scripts/eval_intent.py), [RAG 색인](../backend/scripts/build_vector_index.py), [RAG 평가](../backend/scripts/eval_rag.py), [LLM 답변 평가](../backend/scripts/eval_llm_answers.py).
- RAG 로컬 기록: 공고문 1건·156개 조각의 저장·재열기·검색을 확인했다. 금융교육 자료 전체가 색인됐다는 뜻이 아니다.
- LLM 로컬 기록: EXAONE 3.5 7.8B의 간단한 용어 답변은 확인했지만, 공고 근거 포함 요청에서 3분 시간 초과가 발생했고 실제 API는 원문 대체 응답을 반환했다. 이를 정상 LLM 공고 상담 성공으로 기록하지 않는다.
- 모델 유지 결정: 사용자는 팀과 같은 7.8B를 유지하기로 했다. 모델 교체·유료 API·새 클라우드 자원 도입은 별도 합의한다.
- 리포트 확장, 금융 학습·교육용 RAG, 에이전트별 역할 확장, 알림·배포는 제안과 구현을 구분한다. 기존 화면만으로 자동 리포팅·멀티 에이전트 요구를 충족했다고 주장하지 않는다.
- 모델·벡터 인덱스·DB는 Git 코드와 별도 자산이다. 제출 시 생성/복원·버전·모델 입수·실행 방법이 필요하며 `.env`, 비밀키, 개인정보 덤프를 함께 공개하지 않는다.
