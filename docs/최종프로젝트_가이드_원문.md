- **[기획] 요구사항 정의서**
    
    ## 요구사항 정의서 - 문서
    
    ### 0. 참고 문서
    
    https://docs.google.com/spreadsheets/d/1tOCR4F1uFfWAWSahjcyZifdgyfse-dyX/edit?usp=sharing&ouid=103157838278914841956&rtpof=true&sd=true
    
    ### 1. 목적
    
    - 프로젝트의 **문제, 기능, 범위**를 명확히 정의
    - 팀원 간 **공통 이해 확보**
    - 이후 설계/개발의 기준 문서로 활용
    
    ### 2. 기본 구조
    
    | 요구사항 ID | 요구사항명 | 기능 ID | 기능명 | 상세 설명 | 비고 |
    | --- | --- | --- | --- | --- | --- |
    |  |  |  |  |  |  |
    
    ### 3. 작성 기준
    
    - **요구사항 (큰 기능 단위)**
        - 기능 묶음 단위로 작성
        - 예 : 계정관리, 문서색, 챗봇
    - **기능 (세부 기능)**
        - 반드시 쪼개서 작성
        - “~할 수 있다” 형태
    - **상세 설명 (가장 중요)**
        - 반드시 포함 : 입력 / 처리 / 출력
        - 예 : 사용자가 질문을 입력하면, 문서를 검색하고 LLM이 답변을 생성한다
    
    ### 4. 작성 예시
    
    | 요구사항ID | 요구사항명 | 기능ID | 기능명 | 상세설명 |
    | --- | --- | --- | --- | --- |
    | SRCH01 | 문서 검색 | SRCH01-01 | 질문 입력 | 사용자가 질문을 입력할 수 있다 |
    |  |  | SRCH01-02 | 문서 검색 | 질문 기반으로 유사 문서를 검색한다 |
    |  |  | SRCH01-03 | 답변 생성 | 검색된 문서를 기반으로 LLM이 답변 생성 |
    - **ID는 카테고리별 코드를 활용한다.**
        - ACC → 계정
        - SRCH → 검색
        - CHAT → 챗봇
        - DOC → 문서
    
    ### 5. 필수 포함 기능
    
    - 질문 입력
    - 머신러닝/딥러닝 활용 기능
    - 문서 검색 (RAG)
    - 답변 생성 (LLM)
    - 결과 출력
    
    ### 6. 자주 하는 실수
    
    - 기능을 크게 씀 → 반드시 쪼개기
    - 상세 설명 부족 → 입력/처리/출력 작성
    - 머신러닝/딥러닝 역할 없음 → 반드시 포함
    - LLM 역할 없음 → 반드시 포함
    
    ### 7. 작성 Tip
    
    - 기능을 단순 나열하기보다, **사용자 기준의 동작 흐름(입력 → 처리 → 출력)에 따라 작성**하면 더 명확하게 정리할 수 있습니다.
    
- **[기획] WBS**
    
    ## WBS - 문서
    
    ### 0. 참고 문서
    
    https://docs.google.com/spreadsheets/d/1X7pvkNgFPJ1hmwrYr1JavwWWeVCzeVUk/edit?usp=sharing&ouid=103157838278914841956&rtpof=true&sd=true
    
    ### 1. WBS 목적
    
    - 프로젝트를 **작업 단위로 나누고 일정 관리**
    - 누가 / 언제 / 무엇을 하는지 명확히 정의
    
    ### 2. 기본 구조
    
    | 작업 ID | 작업명 | 상세 작업 | 담당자 | 시작일 | 종료일 | 진행률 | 간트차트(선택) |
    | --- | --- | --- | --- | --- | --- | --- | --- |
    |  |  |  |  |  |  |  |  |
    
    ### 3. 작성 기준
    
    - **“기능”이 아니라 “작업”으로 쪼개기**
        - 문서 검색 기능 개발 ❌→ 문서 업로드 구현 / 임베딩 생성 / 검색 API 구현 ⭕
    - **1개 작업 = 1~2일 단위**
        - 너무 크면 관리 불가능
        - 챗봇 개발 ❌ → 질문 입력 구현 / 응답 출력 구현 ⭕
    - **흐름 기준으로 작성**
        - 요구사항 → 설계 → 개발 → 테스트
    - **담당자 반드시 지정**
        - 책임 없는 작업 = 진행 안 됨
    
    ### 4. 작성 예시
    
    | 작업 ID | 작업명 | 상세 작업 | 담당자 | 시작일 | 종료일 | 진행률 |
    | --- | --- | --- | --- | --- | --- | --- |
    | WBS-01 | 기획 | 요구사항 정의서 작성 | A | 03-25 | 03-26 | 100% |
    | WBS-02 | 설계 | 시스템 구조 설계 | B | 03-27 | 03-28 | 0% |
    | WBS-03 | 개발 | 질문 입력 API 구현 | C | 03-29 | 03-30 | 0% |
    | WBS-04 | 개발 | 문서 검색 기능 구현 | D | 03-31 | 04-02 | 0% |
    
    ### 5. 자주 하는 실수
    
    - 작업을 너무 크게 작성
    - 담당자 없음
    - 일정 현실성 없음
    
    ### 6. 작성 Tip
    
    - **작업을 작게 나누고, “누가 언제 무엇을 할 것인지”를 기준으로 정리**하면 더 명확하게 작성할 수 있습니다.
    
- **[기획] 프로젝트 기획서**
    
    ## 프로젝트 기획서 - 문서
    
    ### 0. 참고 문서
    
    https://drive.google.com/file/d/1Pvo6k6pB_OZxSdJT5VaMLVSUu6ZudRtZ/view?usp=sharing
    
    ### 1. 목적
    
    - 프로젝트의 **문제, 해결 방법, 구조, 역할**을 명확히 정의
    - 팀원 및 심사위원에게 **프로젝트 전체 흐름 전달**
    
    ### 2. 구성 항목
    
    - **프로젝트 주제**
        - 무엇을 만드는지, 누구를 위한 서비스인지 한 줄로 서비스 설명
        - 예 : 내부 문서를 기반으로 답변을 제공하는 AI 검색 시스템
    - **문제 정의**
        - 해결하려는 문제, 기존 방식의 한계, 왜 중요한 문제인지를 포함
    - **시스템 구성 (서비스 구조)**
        - 전체 서비스 흐름 설명
        - 입력 → 처리 → 출력 구조 포함
        - 주요 구성 요소 포함 : LLM, DB, API 등
    - **모델링 방안 (기술 구현 방법)**
        - 어떻게 만들 것인지를 설명
        - 모델 사용 방식, 프롬프트 전략, 데이터 활용 방법 등을 포함
    - **사용 데이터**
        - 개발 단계에서 실패하는 것을 방지하기 위해서 반드시 작성
        - 데이터 종류, 데이터 출처 포함
    - **R&R (역할 분담)**
        - 누가 무엇을 하는지를 작성
        - 기획, 데이터, AI, 백엔드, 프론트 등의 역할을 명확히 나눠 제시
    
    ### 3. 작성 핵심 기준
    
    - **문제 → 해결 흐름 유지**
        
        - 기능 나열 ❌ → 문제 해결 중심 ⭕
        
    - **“왜 이 기술인지” 반드시 설명**
        - GPT 사용 ❌ → 문서 기반 답변 생성을 위해 LLM 사용 ⭕
    - **데이터 반드시 명시**
        - 없으면 개발 및 테스트 단계에서 실패할 가능성이 높음
    - **구조는 “흐름”으로 설명**
        - 입력 → 처리 → 출력
    - **역할 분담 명확하게**
        - 명확하게 하지 않으면 차후 팀원과 협업시에 불화가 생길 가능성이 높음
    
    ### 4. 최소 작성 기준
    
    - 문제 정의 포함
    - 시스템 구조 포함
    - 머신러닝/딥러닝 활용 이유 포함
    - LLM 활용 이유 포함
    - 데이터 명시
    - 역할 분담 포함
    
    ### 5. 작성 Tip
    
    - 기능을 먼저 정하지 말고, **“사용자가 무엇을 입력하고 어떤 결과를 받는지”부터 정의한 후 기능을 정리**하면 더 편하게 정리할 수 있습니다.

    - 품질 기준 반드시 포함
    
    ### 4. 작성 TIP
    
    - **“왜 이 데이터를 수집했고, 어디에 쓰는지”** 한 줄로 먼저 정의
    - 그 후 **품질 기준(중복 제거, 필수값, 검증 조건)**을 명확하게 작성

    ## **시스템 아키텍처 - 이미지**
    
    ### 0. 참고 문서
    
    https://drive.google.com/file/d/1J6AxvaiB9t1If-SxVs1nJYtQdrsnDC_S/view?usp=sharing
    
    ### 1. 목적
    
    - 시스템 전체 구조를 한눈에 이해 가능하게 표현
    - 기능, 데이터 흐름, 기술 스택을 계층별로 정리
        
        → 핵심: “구조를 보여주는 그림”
        
    
    ### 2. 구성 방법 (그리는 순서)
    
    - **상단: Service Layer**
        - 사용자 기능을 먼저 배치
        - 기능 단위로 박스 구성 (챗봇, 추천, 생성 등)
        
        → “사용자가 무엇을 쓰는지”부터 보여줌
        
    - **중단: 처리 로직 (RAG / AI Layer)**
        - 검색, 추론, 모델 처리 영역
        - 역할별로 구분 (예: 검색 / 추론 / 생성)
        
        → 하나로 뭉치지 말고 “역할 기준”으로 나누기
        
    - **하단: 데이터 레이어**
        - 사용하는 DB / 저장소 배치
        - 종류별로 분리 (Vector / Graph / Ontology 등)
        
        → 기술이 아니라 “데이터 역할 기준”으로 배치
        
    - **연결선 (Flow)**
        - 위 → 아래 방향으로 흐름 표시
        - 사용자 → 처리 → 데이터 → 결과 구조
        
        → 화살표는 최소화하고 “핵심 흐름만”
        
    
    ### 3. 작성 기준
    
    - 계층 구조로 그릴 것 (위 → 아래)
    - 박스는 “역할 단위”로 나눌 것 (기술 단위 X)
    - 같은 레벨은 같은 크기/정렬 유지
    - 텍스트는 짧게 (키워드 중심)
    
    ### 4. 필수 포함 요소
    
    - 사용자 기능 영역 (Service)
    - 처리/모델 영역 (AI/RAG)
    - 데이터 저장 영역 (DB)
    - 데이터 흐름 (화살표)
    
    ### 5. 작성 TIP
    
    - **“기능 → 처리 → 데이터” 순서**로 그리면 거의 틀리지 않음
    - **박스 이름은 기술명이 아니라 역할로 작성**

    ### 0. 참고 문서

    ### 1. 목적
    
    - 서비스의 **UI 구조와 기능을 명확하게 정의**
    - 개발 전에 **화면 흐름과 동작을 확정**
    
    ### 2. 기본 구성
    
    - **화면 정보**
        - 각 화면마다 반드시 작성
        - 포함 항목
            - 화면명
            - 화면 경로
            - 요구사항 ID
            - 화면 ID
    - **화면 설명 (Description)**
        - 화면의 목적 + 기능 설명
        - 작성 기준
            - 이 화면이 무엇을 하는지
            - 어떤 기능이 있는지
        - 예
            - 사용자 로그인 유도 및 서비스 진입
    - **UI 요소 정의**
        - 작성 방식
            - 화면 안의 모든 요소를 번호로 구분
            - 각 요소별 기능 설명
        - 예시
            
            
            | 번호 | 요소명 | 설명 |
            | --- | --- | --- |
            | 1 | 로그인 버튼 | 클릭 시 Google 로그인 페이지 이동 |
            | 2 | 질문 입력창 | 사용자가 질문 입력 |
            | 3 | 전송 버튼 | 질문을 LLM으로 전달 |
    - **Check Point**
        - “이 화면이 제대로 동작하는 기준”
        - 작성 기준
            - 동작 조건
            - 제한 사항
            - 예외 처리
        - 예시
            - 로그인 안 된 경우 입력창 비활성화
            - 파일 업로드 최대 4개 제한
            - CSV 파일은 1개만 허용
    
    ### 3. 작성 기준
    
    - **화면 단위로 작성**
        - 페이지 하나 = 문서 하나
    - **“UI + 기능” 같이 작성**
        
        디자인만 설명 ❌ → 클릭하면 어떻게 되는지까지 작성 ⭕
        
    - **사용자 행동 기준**
        - 클릭 / 입력 / 결과 중심
    - **예외 상황 반드시 포함**
    
    ### 4. 작성 Tip
    
    - 화면을 그린 후, **“사용자가 어디를 클릭하면 어떤 결과가 나오는지”를 기준으로 기능을 하나씩 정의**하는 식으로 완성하면 됩니다.

    ## 시스템 구성도 - 이미지
    
    ### 0. 참고 문서
    
    https://drive.google.com/file/d/1mkRePp8gKqcXZUWByRm3b2lH7cP71YmM/view?usp=sharing
    
    ### 1. 목적
    
    - 시스템의 전체 구성 요소와 연결 관계를 시각적으로 표현
    - 인프라, 서버, DB, 외부 서비스 간 구조를 명확히 전달
        
        → 핵심: “무엇이 어디에 있고 어떻게 연결되는지”
        
    
    ### 2. 구성 방법 (그리는 순서)
    
    - **사용자 (Client)**
        - 가장 왼쪽 또는 상단에 배치
        - Web / App / API Client 등
    - **서비스 진입점 (Entry Point)**
        - 웹 서버, API Gateway, Load Balancer 등
        - 외부 요청이 처음 들어오는 지점
    - **애플리케이션 서버**
        - Backend 서버 (FastAPI, Django 등)
        - 기능별로 분리 가능 (API / AI / RAG 등)
    - **처리 영역 (Core Logic)**
        - 비즈니스 로직
        - AI 처리, 검색, 추천 등
        
        → 필요 시 모듈 단위로 분리
        
    - **데이터 저장소**
        - RDB (MySQL, PostgreSQL)
        - Cache (Redis)
        - Object Storage (S3)
        - VectorDB / GraphDB 등
    - **외부 서비스**
        - LLM API
        - 외부 서버 / GPU 서버
        - 서드파티 API
        
        → 시스템 밖에 따로 구분해서 배치
        
    - **인프라 영역**
        - AWS, GCP 등 클라우드
        - EC2, Docker 등 실행 환경
        
        → 전체를 감싸는 구조로 표현
        
    
    ### 3. 연결 방식
    
    - 요청 흐름 기준으로 화살표 작성
        - User → Server → DB → 결과
    - 양방향 필요한 경우만 ↔ 사용
    - 복잡한 연결은 줄이고 핵심 흐름만 표현
    
    ### 4. 작성 기준
    
    - 좌 → 우 또는 상 → 하 방향으로 통일
    - 박스는 역할 기준으로 분리 (서버, DB, 외부 등)
    - 같은 종류는 같은 스타일 유지
    - 텍스트는 최소화 (키워드 중심)
    
    ### 5. 필수 포함 요소
    
    - 사용자
    - 서버 (Frontend / Backend)
    - 데이터 저장소
    - 외부 서비스
    - 인프라 환경
    - 요청 흐름 (화살표)
    
    ### 6. 작성 TIP
    
    - **“요청이 어디서 시작해서 어디까지 가는지”** 먼저 그리고 나머지 채우기
    - **DB/외부 서비스는 반드시 내부 시스템과 구분**해서 표현

    ## 데이터베이스 설계 문서 - 문서
    
    ### 0. 참고 문서

    ### 1. 목적
    
    - 서비스 기능을 데이터 구조로 설계하고, 관계와 흐름을 정의
    - 데이터 저장뿐 아니라 **조회/기능 구현 기준**을 명확히 하기 위함

    ### 2. 구성 항목
    
    - **개요**
        - 시스템 목적
        - 데이터 흐름 (저장 → 처리 → 활용)
    - **요구사항**
        - 기능 기준으로 필요한 데이터 정의
        - 기능 ↔ 테이블 매핑
    - **엔티티 / 테이블 정의**
        - 테이블명
        - 주요 컬럼 (PK, FK, 필수값)
        - 역할 설명
    - **관계 설계**
        - 테이블 간 관계 (1:N, N:M)
        - 실제 서비스 기준 관계 설명
    - **제약 조건**
        - PK, FK
        - Unique
        - Not Null
        - CHECK / DEFAULT
        
        → 데이터 무결성 핵심
        
    - **정합성 및 무결성**
        - FK 기반 참조 구조
        - 삭제 정책 (CASCADE 등)
        - 중복 방지 전략
    
    ### 3. 작성 기준
    
    - 기능 중심으로 설계 (DB → 기능이 아니라 기능 → DB)
    - 관계 구조 명확히 표현
    - PK/FK 반드시 명시
    - 제약 조건 포함
    - 실제 서비스 흐름과 연결
    
    ### 4. 작성 TIP
    
    - **“이 테이블이 어떤 기능을 위한 것인지”** 먼저 정의
    - ERD는 기능 흐름 기준으로 설명 (댓글, 좋아요 등)
    - FK와 CASCADE 정책은 반드시 명시

    - 전처리 순서가 논리적으로 이어지도록 구성

    ## 중간 발표 PT 자료 - PPT문서 (15~20분 발표)
    
    ### 0. 참고 문서

    - 왜 이 문제가 중요한지, 실제로 어떤 불편이 있는지 제시
    - 대상 사용자와 사용 상황을 명확하게 제시
    
    ### 2. 서비스 개요
    
    - 우리가 제안하는 서비스/시스템을 한 문장으로 설명
    - 기존 방식 대비 어떤 점을 개선하는지 강조
        - 구체적인 수치가 있으면 신뢰도 상승
    - 간단한 사용 흐름 제시
    
    ### 3. 시스템 구조 (아키텍처)
    
    - 사용자 입력 → 처리 → 결과까지의 전체 흐름 설명
    - 주요 구성 요소(LLM, DB, API 등)와 데이터 흐름 중심으로 설명
    - 사용 데이터(문서, 로그 등) 명확히 제시
    
    ### 4. 사용 기술 스택
    
    - 사용한 기술과 그 선택 이유를 간단히 설명
    - 문제 해결에 어떤 역할을 하는지 중심으로 정리
    
    ### 5. 현재까지 구현 내용
    
    - 현재까지 구현된 기능과 진행 상황 설명
    - 실제 동작 가능한 부분 위주로 명확하게 전달
    - 현재 부족한 점 or 문제점 1 ~ 2개 / 해결책을 미리 제시하여, 심사위원의 질문 차단
    
    ### 6. 데모
    
    - 입력 → 처리 → 결과 출력 흐름을 시연
    - 핵심 기능이 정상 동작하는지 보여주는 것이 중요
    - 현장 시연 불가한 상황 대비하여 대체 시나리오 준비 (영상, 캡처 등)

    - 남은 작업과 개선 방향을 구체적으로 설명
        - 중요도에 따른 우선순위 설정

    - 나올만한 질문 LIST
        - 이 프로젝트가 실제로 어떤 문제를 해결하나요?
        - 이 서비스를 누가 사용하나요?
        - 기존 서비스와 차별점은 무엇인가요?
        - 이 프로젝트가 시장에서 필요하다고 생각하나요?
        - 수익화 가능성은 있나요?
        - 실제 기업에서 사용할 수 있다고 생각하나요?
        - 사용자 흐름(User Flow)을 설명해보세요
        - 핵심 기능은 무엇인가요?
        - 왜 이 기능이 가장 중요하다고 생각했나요?
        - 기능이 너무 많은데, 우선순위는 어떻게 정했나요?
        - 본인이 사용자라면 이 서비스를 계속 사용할까요?
        - 실패하거나 개선이 필요한 부분은 무엇인가요?
        - 왜 LLM을 사용했나요? 다른 방법으로는 안 되나요?
        - RAG를 적용했다면, 검색 성능은 어떻게 개선했나요?
        - 프롬프트는 어떻게 설계했나요?

        - 이 시스템의 한계는 무엇인가요?

        - Git clone
        - 가상환경 설정
        - 패키지 설치

        - 실행 방법
    - 시스템 구조
        - Frontend / Backend 구조
        - LLM 연동 방식
        - DB 구조
        
        → RAG, GraphDB, VectorDB 연결 구조 포함
        
    - 주요 기능
        - 챗봇 / 질의응답
        - 콘텐츠 생성 (영상 등)

        - LLM 처리 모듈

        - 주요 디렉토리 구조
        - 실행 파일 위치

    - 결과 및 한계
        - 구현 결과
        - 성능
        - 개선 필요 사항
    
    ### 3. 작성 기준

    ## 최종 발표 PT 자료 - PPT 문서 (20~25분 발표)
    
    ### 0. 참고 문서
    
    https://drive.google.com/file/d/13Mv9u3Q4F90tXlHQTDwjSGf7HKWjTLOg/view?usp=sharing
    
    ### 1. 문제 정의
    
    - 기존 문제 + 실제 사례 (왜곡, 불편 등)
    - 데이터 기반 근거 (검색량, 사용자 증가 등)
        
        → “문제가 있다” → “증명된 문제다”
        
    
    ### 2. 해결 전략
    
    - 단순 서비스 소개 ❌
    - 문제 → 해결 방식 매핑
    - 예:
        - 긴 영상 → 숏폼
        - 환각 → RAG
        - 단순 검색 → Graph 추론
        
        → “기능 설명”이 아니라 “문제 해결 구조”
        
    
    ### 3. 서비스 개요
    
    - 한 줄 정의
    - 핵심 기능 3~4개
        
        → 기능 나열 말고 “핵심 축”으로 묶기
        
    
    ### 4. 사용자 흐름 (User Journey)
    
    - 실제 사용 시나리오 단계별 설명
    - Discover → Ask → Explore → Engage 흐름
    
    ### 5. 시스템 아키텍처
    
    - 전체 구조 (Service / RAG / Data)
    - 데이터 흐름 중심 설명
        
        → 반드시 “왜 이렇게 나눴는지” 포함
        
    
    ### 6. 데이터 아키텍처
    
    - 서비스에서 사용하는 데이터 구조와 흐름 설명
    - 어떤 데이터를 어디에 저장하고 어떻게 활용하는지 정리
    - **포함 내용**
        - 데이터 종류 (사용자 데이터, 콘텐츠 데이터 등)
        - 저장 구조 (DB, 파일, 캐시 등)
        - 데이터 흐름 (수집 → 저장 → 조회 → 활용)
        - (선택) RAG 사용 시 데이터 구성 (문서, 임베딩 등)
        
        → 핵심: “데이터가 어떻게 흐르고 쓰이는지”
        
    
    ### 7. AI / LLM 활용 구조
    
    - 서비스에서 AI/LLM이 어떤 역할을 하는지 설명
    - 입력 → 처리 → 출력 흐름 중심으로 정리
    - **포함 내용**
        - LLM 사용 목적 (생성, 요약, 질의응답 등)
        - 처리 흐름 (입력 → LLM → 결과)
        - (선택) RAG 구조 (검색 → LLM → 응답)
        - (선택) 추가 처리 (재정렬, 후처리 등)
        
        → 핵심: “AI가 어디에서 어떤 역할을 하는지”
        
    
    ### 8. 실험 및 성능 결과
    
    - 정확도 / 응답속도 / 개선 결과
    - 비교 (Before vs After)
        
        → 수치 없으면 감점 요소
        
    
    ### 9. 서비스 구현
    
    - 실제 기능 동작 방식
    - 파이프라인 설명
    - 예:
        - 추천 시스템 흐름
        - 챗봇 처리 구조
    
    ### 10. 데모
    
    - 반드시 포함
    - 실패 대비 영상 준비
        
        → “동작한다”를 증명하는 파트
        
    
    ### 11. 기술 스택 & 인프라
    
    - 단순 나열 금지
    - 역할 중심 설명
        
        → “왜 이 기술을 썼는지”
        
    
    ### 12. 결과 및 성과
    
    - 성능 결과
    - 사용자 가치
    - 차별성
    - 예:
        - 정확도 91%
        - 응답 속도 20초 이내
    
    ### 13. 한계 및 개선
    
    - 문제점 솔직하게
    - 개선 방향 제시
        
        → 질문 선제 차단
        
    
    ### 14. 결론 / 확장성
    
    - 서비스 가치
    - 향후 확장 계획
        
        → “이거 실제로 쓸 수 있다” 강조
        
    
    ### 15. Q&A 대비
    
    - 기술 / 비즈니스 / 구조 질문 대비
    - 모르면 확장 의지로 답변
    
    ### 16. 작성 기준
    
    - 슬라이드 = 설명서가 아님 (키워드 중심)
    - “왜?” 중심으로 설명
    - 비교 / 실험 / 수치 반드시 포함
    - 그림(아키텍처, 흐름) 필수
    
    ### 17. 작성 TIP
    
    - 한 슬라이드에 메시지는 하나만 넣기
        - 한 장에 여러 얘기 넣으면 전달력 바로 떨어짐
    - 제목만 봐도 내용이 이해되게 작성
    - 텍스트 줄이고 “도식(그림)”으로 설명

## 8. 프로젝트 간 지켜야 할 사항

### 1. 기술에 너무 매몰되지 말자

- 특정 기술을 써보고 싶은 것은 좋지만, 팀 전체가 이해하지 못하는 기술을 강요하는 것은 지양해야 한다.
- 프로젝트는 개인 실험이 아니라 **팀 결과물**이다.

### 2. 구현 가능성을 항상 먼저 고려하자

- “멋있어 보이는 아이디어”보다 **기간 내 구현 가능한 수준**이 중요하다.
- 기술 난이도와 일정은 반드시 함께 고려해야 한다.

### 3. LLM을 반드시 사용할 이유가 있어야 한다

- 단순 CRUD, 검색, 분류로 해결 가능한 문제를 굳이 LLM으로 풀지 않는다.
- “왜 LLM이 필요한지” 명확히 설명 가능해야 한다.

### 4. 역할 분담은 명확하게 하자

- 누가 무엇을 하는지 애매하면 결국 일부 인원에게 의존하게 되어 일이 몰린다.
- 최소한 기능 단위로라도 책임을 명확히 한다.

### 5. 커뮤니케이션 없이 구현하지 말자

- 기능 추가/변경 시 팀원과 공유 없이 진행하지 않는다.
- “나중에 보여주면 되겠지”는 위험한 생각이다.

### 6. 초반에 설계 없이 바로 구현하지 말자

- 최소한의 구조(아키텍처)는 합의하고 시작한다.
- API 구조, 데이터 흐름 정도는 정의 후 진행한다.

### 7. 데이터 확보 가능성을 반드시 확인하자

- 데이터 없이 시작하면 중간에 막힌다.
- 사용할 데이터의 출처와 확보 방법을 초반에 미리 정의한다.

### 8. 성능보다 흐름을 먼저 완성하자

- 처음부터 최적화에 집착하지 않는다.
- “동작하는 서비스”를 먼저 만든다.

### 9. 에러 처리 및 예외 상황을 고려하자

- 정상 케이스만 생각하면 실제 사용 시 문제가 발생한다.
- 실패 케이스도 반드시 테스트한다.

### 10. 발표를 고려하며 개발하자

- 결과를 “보여줄 수 있어야” 한다.
- 로그만 있는 프로젝트는 좋은 평가를 받기 어렵다.

### 11. 문제가 생기면 숨기지 말자

- 오류나 막힌 부분은 빠르게 공유한다.
- 늦게 공유할수록 해결이 어려워진다.

### 12. 완성도를 우선으로 하자

- “대단한 아이디어”보다 “완성된 프로젝트”가 더 중요하다.
- 끝까지 구현하는 것이 목표다.

### 10. 최종 발표 준비

1. **기술 질문뿐 아니라 서비스 가치 질문도 준비**
    - 개발 실무자뿐 아니라 CEO 도 참석
    - “이 기술을 왜 썼는가?”뿐 아니라 “이 서비스가 실제로 돈이 되는가?”, “누가 쓰는가?”, “기존 서비스와 뭐가 다른가?”에 대해서 질답 준비하기
2. **기획 의도와 문제 정의를 명확히 말할 것**
    - 기능을 많이 만든 것보다 중요한 건 “어떤 문제를 해결하려고 했는지”임.
    - 발표 초반에 문제 상황, 타겟 사용자, 해결 방식이 명확해야 함.
    - 초안을 만들고, 설득력있게 수정하기
3. **핵심 기능 위주로 발표할 것**
    - 만든 기능을 전부 설명하려고 하면 발표가 산만해짐.
    - 사용자가 실제로 가치를 느낄 핵심 기능 2~3개를 중심으로 설명하는 게 좋음.
4. **시연은 반드시 안정적으로 준비**
    - 라이브 시연이 불안하면 녹화 영상도 반드시 준비.
    - 로그인, API 호출, 이미지 업로드, 추천 결과 등 핵심 흐름은 발표 전 여러 번 점검해야 함.
5. **AI 모델은 성능 수치와 한계를 같이 말할 것**
    - 단순히 “AI를 사용했다”가 아니라 어떤 모델을 왜 사용했는지 설명해야 함.
    - 정확도, F1-score, loss, 평가 방식 등 근거가 있어야 함.
    - 모델 한계가 있는 경우, 질문이 나오기전에 고도화방안까지 생각해서 넣어놓기
6. **DB/API/아키텍처는 흐름 중심으로 설명**
    - 프론트 → 백엔드 → AI 서버 → DB → 응답 구조를 명확히 설명.
7. **사용자 시나리오를 넣어주면 뭘 만들었는지 파악하기 용이하다.**
    - 사용자의 문제 상황 → 서비스 이용 흐름 → 최종 결과를 한눈에 보기쉽게 정리
8. **차별점과 경쟁 서비스 비교 준비**
    - “비슷한 서비스가 이미 있지 않나요?”라는 질문이 나올 수 있음.
    - 기존 서비스 대비 차별점, 개선점, 확장 가능성을 준비해야 함.
    - AI를 사용해서 차별화했다 X → AI를 왜 사용했고, 이러한 기대효과를 얻으려고 하였다.
9. **BM 또는 서비스 확장 방향 준비**
    - 실제 서비스 관점에서는 수익화 질문이 나올 수 있음.
    - 현실적인 방향으로 BM 발표
10. **예상 질문 리스트를 만들어 리허설할 것**
- 기술 질문, 기획 질문, 서비스 질문, 한계 질문을 나눠서 준비.
- 모르는 질문이 나오면 억지로 답하지 말고 “현재는 ~까지 구현했고, 향후 ~로 개선할 계획입니다”처럼 답변.
1. **기술적인 부분에서는 발표자가 다 알면 좋지만 설명 불가한 부분에서는 해당 기술 구현한 사람이 대답할 수 있도록 준비**
